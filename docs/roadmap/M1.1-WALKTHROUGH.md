# M1.1-I non-coder walkthrough

This walkthrough uses the local studio only. It does not use a paid service. It does not download content. It does not publish to a remote environment.

The walkthrough is for the current M1.1-I checkpoint. It does not seal the full M1.1 artifact. G/H integration and final coordinator acceptance remain pending.

## 1. Start the local studio

Open a terminal.

Set the repository as the working directory:

```text
cd /home/bobbyranka/Projects/pastel-rts
```

Make a disposable copy of the checked-in fixture pack. This keeps local draft and publication files away from the source fixture:

```text
PACK_DIR="$(mktemp -d /tmp/pastel-rts-m11-i-pack.XXXXXX)"
cp -a /home/bobbyranka/Projects/pastel-rts/content/dev-pack-v2/. "$PACK_DIR"/
```

Start the root studio command:

```text
npm run dev:studio -- --game-port 23373 --foundry-port 23374 --content-port 23387 --pack-dir "$PACK_DIR"
```

Wait for the launcher to print `Studio ready (loopback only)`. This is the readiness result, not a timed sleep. The launcher prints these URLs:

```text
Studio game:       http://127.0.0.1:23373/?mode=interaction-lab&content=studio
Bundled/offline:   http://127.0.0.1:23373/?mode=interaction-lab
Foundry:           http://127.0.0.1:23374/
Content:           http://127.0.0.1:23387/health
```

Use the `Studio game` URL for Foundry-published content. It has the explicit `content=studio` query. Do not remove that query.

Use the `Bundled/offline` URL for the normal standalone runtime. It has no `content=studio` query. The runtime then uses the bundled pack. This preserves the normal standalone bundled default.

Optional health check:

```text
curl -fsS http://127.0.0.1:23387/health
```

A healthy fixture reports `ok: true`, current revision `3`, draft revision `3`, and `restartRequired: false` in the current pack.

Stop the studio with Ctrl-C in the launcher terminal. The launcher must free 23373, 23374, and 23387. Do not stop an unrelated service on 8787.

The editor saves the local changes to the disposable content service. It does not publish them. The draft is now different from the current published revision.

## Draft versus Published

Draft:

- belongs to the local content service;
- changes after `Replace source PNG` and field edits;
- is created by `Save draft`;
- is checked by `Validate saved draft`;
- is used by `Preview draft`;
- is not live in the normal runtime until `Publish revision`.

Published:

- is an immutable numbered revision;
- is created by `Publish revision`;
- is the content used by the explicit studio runtime route;
- requires runtime acknowledgement, and sometimes a restart;
- remains available as retained source content after a replacement or revert.

Source preservation:

- The stable ID remains the runtime identity.
- Replacing a PNG does not create a new stable ID.
- The prior publication source remains retained.
- Revert publishes from retained source content. It does not erase originals.
- Runtime art and reference art are separate.

## Browser export and reproduction

1. Open the bundled interaction lab or the studio game with the revision you need.
2. Select a friendly unit. Click empty ground to move it. Confirm that it moves.
3. Select `Export bug bundle`. Save the downloaded JSON file.
4. Open a fresh browser tab with the same content source and revision. For studio content, use `Select revision` to load the revision recorded in the bundle first.
5. Select `Reproduce bug bundle`. Choose the saved JSON file.
6. Confirm the status `Bug bundle reproduced: ... checksum samples matched exactly.` The replay uses the scene, seed, ordered commands and checksum sequence in the bundle.

The bundle contains JSON scene data and identity metadata, not image files. It is labelled `json-only`. The exact content revision must already be active. A missing, unknown, altered or mismatched revision is rejected visibly; the current scene remains intact. Do not place credentials or private local paths in diagnostic text or reproduction steps.

Coordinator verification after G2 used an actual pointer move, a non-empty accepted command log, a fresh browser context and exact checksum-array comparison. Both reproduction and invalid-revision preservation tests passed.

## Offline production preview

Build the web bundle:

```text
npm run build
```

Stop the content server. Start the production preview:

```text
npm run preview --workspace @pastel-rts/game-web -- --host 127.0.0.1 --port 23373 --strictPort
```

Open the bundled route:

```text
http://127.0.0.1:23373/?mode=interaction-lab
```

This route reads the relative pack at:

```text
./content/dev-pack-v2/pack.json
```

The production check passed with pack HTTP 200, no `/dev-content` requests, no EventSource requests, and no page exceptions.

For the relative iOS bundle after a web build, the repository command is:

```text
npm run ios:sync-web
```

That command copies `apps/game-web/dist` into `apps/ios-shell/PastelRTS/WebGame`. The Vite build uses `base: './'`, and the content client resolves `./content/dev-pack-v2/` relative to the local bundle. The native shell must load the local `pastel://` bundle. It must not use the studio content server.
