Publication storage

Each pack gets a local .content-publication directory:

- state.json stores currentRevision and draftRevision.
- draft-pack.json stores the mutable v2 authoring view.
- revisions/<revision>/pack.json stores the immutable published v2 manifest.
- revisions/<revision>/pack-v1.json stores the compatible v1 manifest.
- revisions/<revision>/metadata.json stores validated immutable revision metadata.
- revisions/<revision>/assets/ stores immutable copies of runtime and data assets.
- references.json stores reference attachment metadata.
- references/<id>/<sha256>.png stores retained reference images.

Revision metadata has this shape:

{
  "schemaVersion": 1,
  "revision": "2",
  "packId": "dev-pack-v2",
  "manifestPath": ".content-publication/revisions/2/pack.json",
  "legacyManifestPath": ".content-publication/revisions/2/pack-v1.json",
  "manifestHash": "<lowercase sha256>",
  "visualContentHash": "<lowercase sha256>",
  "simulationRulesHash": "<lowercase sha256>",
  "restartRequired": true,
  "assets": [
    {
      "kind": "runtime",
      "assetPath": "units/example/sheet.png",
      "storagePath": ".content-publication/revisions/2/assets/units/example/sheet.png",
      "sha256": "<lowercase sha256>",
      "byteLength": 70,
      "width": 1,
      "height": 1
    }
  ],
  "createdAt": "<ISO timestamp>",
  "parentRevision": "1"
}

The source revision field is present on a revert publication. It identifies the retained revision used as rollback content.

Runtime hash rules

- visualContentHash covers presentation fields for units and buildings and the hashes of runtime assets.
- simulationRulesHash covers enabled state, faction, movement, radii, footprints, terrain rules, placement points, map/scenario references, and data asset hashes.
- Hash input uses deterministic canonical JSON. Object keys are sorted. Unit and building lists and asset lists are sorted by stable identifiers or paths.
- A simulation-rules hash change sets restartRequired to true. Draft edits do not change the current publication.

HTTP API

GET /pack

Returns the current published v1 pack.

GET /pack?schema=2

Returns the current published v2 pack. It does not return the mutable draft.

GET /v2/publication

Returns:

{
  "currentRevision": "2",
  "draftRevision": "3",
  "current": <RevisionMetadata>
}

GET /v2/revisions

Returns all retained metadata, sorted by revision, plus current and draft cursors:

{
  "schemaVersion": 1,
  "currentRevision": "2",
  "draftRevision": "3",
  "current": <RevisionMetadata>,
  "revisions": [<RevisionMetadata>]
}

GET /v2/revisions/:revision

Returns one retained RevisionMetadata object. The revision is decoded and checked as a single safe path segment.

POST /v2/publish

Publishes the current draft only when the caller still sees the expected current publication:

{
  "expectedRevision": "2"
}

Success returns:

{
  "ok": true,
  "revision": "4",
  "metadata": <RevisionMetadata>,
  "pack": <published PackV2>,
  "publication": <publication status>
}

The new revision directory is assembled in a temporary directory and renamed into place. The publication state is written only after the snapshot validates. A failure leaves the prior current revision readable.

POST /v2/revert

Creates a new publication from retained content. It does not move or delete the target revision:

{
  "targetRevision": "2",
  "expectedCurrentRevision": "4"
}

Success has the same result shape as publish. The new metadata contains parentRevision equal to the prior current revision and sourceRevision equal to targetRevision.

Draft unit and building API

The existing routes remain draft authoring routes. They accept optional expectedRevision or expectedDraftRevision. Callers should send the draftRevision returned by /v2/publication or by a draft mutation response.

- POST /v2/units
  { "archetype": <UnitArchetype>, "pngBase64": "...", "expectedRevision": "3" }
- PUT /v2/units/:id
  { "archetype": <UnitArchetype>, "pngBase64": "...", "expectedRevision": "3" }
- PATCH /v2/units/:id
  { "enabled": true, "expectedRevision": "3" }
- DELETE /v2/units/:id?force=true
  Optional JSON body: { "expectedRevision": "3" }. An empty body remains compatible.
- POST /v2/units/:id/duplicate
  { "newId": "scout-copy", "displayName": "Scout Copy", "expectedRevision": "3" }

Building routes use the same payloads and substitutions:

- POST /v2/buildings
- PUT /v2/buildings/:id
- PATCH /v2/buildings/:id
- DELETE /v2/buildings/:id?force=true
- POST /v2/buildings/:id/duplicate

Draft mutation success returns the existing result fields plus:

{
  "draft": <draft PackV2>,
  "publication": <publication status>
}

A stale draft mutation returns HTTP 409:

{
  "error": "Stale draft revision. Expected 1, but the current draft revision is 2. Refresh revision 2 before retrying.",
  "code": "revision-conflict",
  "scope": "draft",
  "expectedRevision": "1",
  "currentRevision": "2",
  "currentPublicationRevision": "1",
  "current": <current published RevisionMetadata>
}

A stale publication mutation returns the same error code with scope publication and currentRevision equal to the current publication revision. A dependency-blocked removal returns HTTP 409:

{
  "error": "unit scout is referenced by scenarios: lab-skirmish",
  "code": "dependency-conflict",
  "dependencies": ["lab-skirmish"]
}

Use force=true only when the editor wants the documented warning. Publication still rejects a scenario with a missing archetype.

Reference attachment API

Reference art is not inserted into PackV2, revision assets, or runtime asset serving.

- POST /v2/references
  { "id": "concept-scout", "displayName": "Concept Scout", "pngBase64": "..." }
- GET /v2/references
  { "references": [<ReferenceAttachmentMetadata>] }
- DELETE /v2/references/:id

Reference images are content-addressed and are retained after metadata removal. They are not copied into a publication.

Validation and safety

- IDs use the existing lowercase stable-ID policy and a maximum length of 64.
- Asset paths are relative and reject empty, absolute, dot, dot-dot, backslash, NUL, colon, malformed, and repeatedly encoded traversal forms.
- PNG uploads have an 8 MiB byte limit, 4096-pixel maximum dimension, and 16,777,216-pixel maximum area.
- PNG files are decoded before storage. Signature-only acceptance is not used. Chunk bounds, CRCs, zlib data, scanline length, filters, supported color types, palettes, transparency, and non-interlaced encoding are checked.
- Unit and building schemas validate source dimensions. Existing animation validation rejects missing or out-of-range frame references. No animation frames are fabricated.
- Published manifests and assets are copied to revision-specific storage. Authoring replacement of a stable ID can replace the mutable draft image, but it cannot overwrite a retained revision source.
- Failed validation and failed snapshot creation occur before the publication state changes. Revert copies retained content and writes a new revision.

Known limitations

- This is a local single-server foundation. The server binds to 127.0.0.1. No public service, deployment, authentication, or multi-process locking was added.
- Existing v2 client code was intentionally not changed. The later UI lane must send draft preconditions and expose publish/revert actions.
- Historical assets are retained on disk and listed in metadata. HTTP asset serving is for the current publication only; there is no historical asset download route.
- Interlaced PNG files are rejected. The PNG decoder accepts the supported non-interlaced color types and bit depths required by the authoring contract.
- Initial migration permits missing source files so an existing legacy pack can receive publication state. An explicit publish requires every referenced runtime and data asset to exist and validate.
- Optional expected revisions preserve old callers but provide no concurrency protection when omitted.
- Reference metadata has list, create, and delete operations. It has no UI and does not participate in publication.
