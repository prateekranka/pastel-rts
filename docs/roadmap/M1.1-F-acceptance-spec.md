# M1.1-F independent acceptance specification

Status: implemented and independently executed; see `M1.1-F-handoff.md`.

## Goal

Verify the integrated A2 backend and D Foundry workflow through real Playwright browser sessions and the real content server. Preserve the existing observable validation intent. Keep runtime E failures visible and separate from available Foundry/API evidence.

## Test boundary

Allowed writes are limited to:

- root `package.json` for Foundry root test coverage;
- `playwright.config.ts`;
- `apps/game-web/e2e/**`;
- `apps/foundry/e2e/**`;
- `docs/roadmap/M1.1-F-*`.

No product source, schemas, fixtures, lockfile, native file, snapshot, or other script is changed by this acceptance lane. Tests write only to a unique temporary copy of `content/dev-pack-v2` and to the configured Playwright artifact directory.

## Runtime setup

- game: `http://127.0.0.1:20373`;
- Foundry: `http://127.0.0.1:20374`;
- content: `http://127.0.0.1:20387`;
- pack: a fresh temporary copy of the original `content/dev-pack-v2`;
- browser: installed Playwright Chromium, without security-disabling switches;
- allowed host adjustment: `ignoreDefaultArgs=--disable-dev-shm-usage` only when needed;
- screenshots: composited `page.screenshot`, at 1280x800 and 1194x834.

The Playwright configuration and test helper must use the same configured game origin. No test may hard-code 5173 for the isolated game.

## Acceptance matrix

### A. Foundry browser workflow

1. Load the library and verify the initial published pack.
2. Search by stable ID and display name. Filter by unit/building type. Toggle disabled entries.
3. Create a unit and a building through the real editor UI with distinct original PNG bytes.
4. Confirm Save draft changes the draft cursor only. The new IDs are absent from the published revision.
5. Confirm Validate saved draft succeeds and the published cursor and pack remain unchanged.
6. Confirm Preview draft reports draft-only behavior.
7. Confirm Publish revision creates a new immutable revision containing the exact IDs and asset hashes.
8. Replace an existing stable ID with a second distinct PNG. Change world scale and idle/move FPS. Confirm the ID is unchanged, fields persist after reload, and both source originals remain content-addressed.
9. Exercise undo/redo and dirty navigation confirmation. Do not discard a dirty editor without a visible confirmation.
10. Exercise duplicate, enable/disable, dependency-aware remove, and force-remove warning.
11. Attach a reference PNG. Confirm it is visible in the reference panel and absent from published runtime assets.
12. Revert to a retained revision. Confirm the new publication points to the retained source content and the source bytes remain readable.

### B. API and integrity acceptance

Against the real server, test:

- exact stable IDs, PackV2 content hash and per-asset SHA-256 after publication;
- exact source byte equality for two same-ID unpublished replacements;
- source originals still present after failed publication and draft removal;
- corrupt PNG and invalid PNG rejection;
- oversized request/upload rejection;
- missing frame data rejected by validation or publication;
- stale concurrent draft mutation returns revision conflict;
- failed publication leaves the last-good current revision, hash, bytes, and cursors unchanged;
- reference image round trip is separate from revision asset metadata;
- unsafe historical/draft asset access is rejected.

These are API acceptance checks. They must not mock fetch or substitute a fake server.

### C. Existing game audit maintenance

- Use the actual configured isolated game origin in the sandbox launcher test.
- Replace the old `typeof replayMatched === 'boolean'` assertion with a true equal-checksum replay result when the runtime exposes it.
- If runtime E cannot replay deterministically, keep the test failure and document the exact result. Do not skip, loosen, or rebaseline it.
- Keep the existing blocker, save/load, and replay observability intent.

### D. Visual engineering review

Capture the actual original-art fixture at both target viewport sizes. Inspect it against the old expected lab screenshot. Record concrete differences in the F handoff, including whether original-art replacement alone explains the pixel delta. Do not update a snapshot unless the mismatch is fully explained and there is no layout, input, or render regression. The result is an engineering regression verdict, not human design acceptance or device performance proof.

## Completion criteria

The F handoff must state actual commands and results, exact screenshots and sidecars, browser and server diagnostics, passing and failing tests, reproduction steps for every new defect, and separate engineering, human-design, and physical-device status. No M1.1 or later roadmap status is advanced.
